# Voice — the throughline for every card field (skill + collection)

Every field — names, blurbs, "What it does", "When to use it", FAQ — shares one voice:
**honest, glanceable, human.** The copy fills a real page that has to earn a click, rank in
search, and get quoted verbatim by an AI answer engine. Write for all three. The section
guides assume this file; they don't restate it.

## Write like this
- **Outcome over mechanism.** Lead with what the user gets; front-load the payoff in the first
  few words.
- **Concrete over hype.** A real artifact or number ("14 dimension scores", "a 30-second MP4")
  beats "powerful", "seamless", "comprehensive". Don't claim what the source can't back.
- **Second person, present tense, tight.** "You paste a repo URL and get…", never "This skill
  allows you to…" or "Users can…".
- **Keyword-natural, never stuffed.** Work the real subject terms in once or twice, where they
  read naturally.
- **Self-contained.** Meta descriptions, cards, blurbs, and quoted FAQ answers show with no
  surrounding context. Each must stand alone, not lean on the H1 or nearby text.
- **Customer language**, not internal jargon or the command name.

## Names and blurbs
The blurb (`shortDescription` / `description.short`) doubles as the hero lead, the SEO meta
description, and the card blurb. Make it one self-contained claim, outcome first, in plain
verbs ("turn", "build", "ship", not "leverage", "streamline"). The name is a title, not a
tagline or feature list. Match every claim to what the README actually ships.

**Hard limit: 200 characters.** Publish rejects a longer blurb (`validateCollection` /
`validateSkill`). Write to the meaning, not the cap; if it runs long, cut a clause rather than
padding to fill it. One or two sentences is plenty.

## Humanize — the pass before finalizing
AI copy has tells. Cut them: no inflated significance ("stands as a testament to"); no
rule-of-three ("faster, smarter, simpler"); **no em/en dashes** (use a period or comma; scan
for — and – before saving); no "-ing" filler ("…, enabling teams to…"); no vague attributions
("experts say"). Vary sentence length. Prefer is/are/has over "serves as", "boasts".

## Good vs. bad
Bad: "This groundbreaking skill stands as a testament to modern automation, turning any
codebase into a clear, comprehensive, and compelling map, empowering developers everywhere."
Good: "Point it at any repo and get a labeled map of how the code fits together: entry points,
the modules that matter, and how data moves between them. No setup, no diagrams to draw by hand."
